# AI 工作流说明

题目允许使用 AI 编程工具，并要求说明**怎么用**。这份文档记录本次实现的实际流程，
用过程中真实发生过的事情举例（包括 AI 写错、我自己判断错、以及最后怎么发现并修掉）。
不包含私人聊天记录、账号或完整提示词。

---

## 1. 一句话概括

AI 负责"把已经想清楚的东西快速写出来"，我负责**决定写什么、判断写得对不对**。
分界线是一个很实际的标准：**任何结论都必须有一条自己能跑的命令或一张自己截的图作证**，
AI 说"已完成"不算证据。

---

## 2. 拆解：先把题拆成可验收的碎片

第一步不是写代码，是读题并把 14 条需求（R-01 ~ R-14）摊平成一张表，
然后问一个具体问题：**每条需求，我用什么动作证明它成立？**

比如 R-05 写的是"查询接口不应通过查询请求驱动任务推进"。这句话可以直接翻译成可执行的检查：

```bash
# 连查 10 次，status 与 updated_at 都不许变
for i in $(seq 10); do curl -s localhost:8090/api/tasks/$ID | jq -r '.status, .updatedAt'; done
```

R-07 的"查询异常不能把任务标成失败"也一样，落成一条前端单测：
mock 掉 fetch 让它 reject，断言 `task.status` 仍是 `PROCESSING`、只有 `queryState` 变 `error`。

**这带来的差别很大**：含糊的"做完了异步状态管理"没法验证，而"连查 10 次字段不变"跑一下就知道对错。
拆解结果写在 [plan.md](../plan.md) 的 §5 与 §6（需求追溯矩阵），后面每一步都对着它做。

---

## 3. 提供上下文：契约先行

AI 最容易犯的错不是写不出代码，而是**前后端各写一套字段**。所以第二步是把
[docs/api.md](api.md) 先写死：路径、字段名、状态枚举、错误码、HTTP 状态码，全部定下来。

这份契约在后续所有对话里都是最高优先级的上下文。效果：

- 后端按 §4.1 返回 `TaskDto`，前端按同一节写 `types.ts`，不需要来回问"你那边字段叫什么"。
- 出现分歧时**改契约文件**，而不是在两边各打补丁。P3 把提交接口从"只返回 3 个字段"
  改成返回完整 `TaskDto`，就是先改 `docs/api.md §4.1`，再改两边代码。

除了契约，稳定的上下文还有：`plan.md`（现在做到哪、下一步是什么）、
`README.md`（对外可见的行为说明）、以及每个模块顶部那段解释"为什么这样做"的注释。
后者看着像废话，实际很关键——AI 修改代码时如果只看到"做了什么"，很容易把
"为什么不能那样做"的约束一起删掉。典型例子是 `next.config.ts` 里关于
`distDir` 和 `output: "standalone"` 的两段注释，它们挡住了一次"顺手优化"。

---

## 4. 生成与修改：小步、可回退

每个阶段（P0 ~ P8）单独提交，commit message 用 `feat(pN): ...`。
好处很直接：某个阶段引入的问题，`git diff` 一看就知道范围；要回退也只回退一个阶段。

具体做法：

1. 先写这一阶段要改的**文件清单**，再逐个写。
2. 后端先跑 `mvn -B test`，前端先跑 `pnpm test`，都过了再起服务。
3. 起服务用真实 HTTP 验证（curl / 浏览器），不满足判据就不进入下一阶段。
4. 阶段结束时把"实际与计划的偏差"写回 `plan.md`——这一条后面救过很多次。

第 4 条不是形式主义。比如 P1 记下的"`app/loading.tsx` 的 Suspense 边界会吞掉 404 状态码"，
到了 P4 加历史页时又遇到同一类问题，翻记录比重新踩一遍快得多。

## 5. 验证：AI 的自测不够，要自己构造敌意输入

这是我认为最值得强调的一点。AI 写完之后自己跑一遍单测、跑一遍正常流程，
结果通常是"绿"，但那只是**happy path 的绿**。真正的问题几乎全在异常路径上。

本次由"真实验证"（而不是单测）暴露出来的问题：

| 问题 | 单测为什么发现不了 | 怎么发现的 |
|---|---|---|
| `mvn spring-boot:run` 在中文路径下 `ClassNotFoundException` | `mvn test` 走 surefire，不经过插件 fork 的 classpath 组装 | 真去启动了一次 |
| 种子数据中文双重编码（`æ—…è¡Œ`） | 测试用的是内存里的字符串，不经过 MySQL 客户端编码协商 | `SELECT HEX(LEFT(title,2))` 查到 `C3A6E28094` |
| 生产构建下不存在的模板返回 200 | 单测只断言 `notFound()` 被调用，不管 HTTP 状态码 | 浏览器 DevTools 看状态码，发现是 200 |
| 并发首屏建用户撞主键 → 500 | 单测里 `UserService` 的 mapper 是 mock，永远不会真的并发 INSERT | 用浏览器打开历史页，日志出现 `Duplicate entry` |
| REPEATABLE READ 下"插入后读不到" | 同上，没有真事务 | 修完上一个 bug 后仍然 500 |

表格里后两行是同一个教训的两个版本：**凡是"首次访问/初始化"的路径，
单测天然覆盖不到并发窗口**。所以验证时我特意连着用 5 个全新 Cookie 打开页面，
而不是测一次就收工。

同理，R-06 的失败注入不是"调一下接口看看能不能失败"，而是三种组合都跑：
`NEXT + GENERATE`（下一个失败、再下一个恢复）、`ALL + ASSET_CHECK`（连续失败）、
`FINALIZE`（前两步成功、最后一步失败且无结果图）。只有第三种能证明"失败后不再产生结果"。

## 6. 修正：改代码前先确认根因

AI 很容易给出"看起来对"的修法。上面第 4 个问题（并发建用户）第一次的修法是
`INSERT ... ON DUPLICATE KEY UPDATE id = id`，逻辑上完全正确，但**修完还是 500**。
如果当时就此收工，就会留下一个只在并发首屏出现的稳定故障。

真正的根因是第二层的：MySQL 默认 REPEATABLE READ，`@Transactional` 里的
"插入后紧接着查"用的是事务开始时的快照。所以修法是**去掉这个事务**——
插入已经幂等，不需要事务包裹，每条语句各自提交即可。

判断"改对了"的标准不是"报错消失了"，而是能解释**为什么原来会错**。
这里能说清：快照读 + 并发提交 = 看不到别人刚写的行；去掉事务 = 每条语句读最新已提交数据。

## 7. 我作为人保留的判断

有几件事我没有交给 AI 决定：

- **不允许伪造成功**。P2 阶段提交按钮的功能还没做，我选择禁用按钮并写明原因，
  而不是让它"看起来能点"。同样，README 里凡是没实测过的都标"未验证"，
  不把"代码写了"当成"功能可用"。
- **不做超出范围的东西**。题面明确不需要 MQ、SSE、重试、模板后台，
  这些一旦动手就会挤掉主线（异步状态与交付质量）。
- **每个"为什么"要能自己讲出来**。如果一段代码我只能复述"AI 说是这样的"，
  那它就不该留在仓库里——要么搞懂，要么删掉。

## 8. 局限与反思

- **AI 生成的测试容易自证**：它可能按自己的实现去写断言，于是测试通过但需求没满足。
  对策是先写"判据"再写实现（例如先定死"查 10 次 `updated_at` 不变"，
  再让它去实现查询接口），而不是写完实现再让它补测试。
- **风格一致性需要人盯**：前后端各自的命名、错误码、注释风格，AI 在不同阶段会漂移，
  靠"契约先写死 + 阶段结束回看 diff"来收敛。
- **AI 对"环境差异"几乎无感**：中文路径、Windows 符号链接、容器里的 `LANG`、
  端口占用，这些只能靠自己实际跑一遍才发现，也正好是本次问题最集中的地方。
